承接 `20260917_FastAPI後端與Supabase上傳.md`。開始手機端，伺服器預計部署在 Railway。

| `mobile-backend/app/main.py` | 獨立 FastAPI app，掛 CORS 與兩組路由 |

## 定案的決策

### 1. 手機端後端獨立子目錄，不與本機服務混在一起

`src/podscript/server.py` 依賴 whisper.cpp／pyannote／Metal GPU，這些完全不能跑在 Railway 上。
手機端只需要「唯讀查詢 + Google 登入」，故開新的 `mobile-backend/`，
與 `src/podscript/` 沒有 import 關係，兩者各自部署、各自的 requirements.txt。

### 2. 前後端分離：Railway（API）+ Firebase Hosting（靜態頁）

討論過三個角度後使用者定案維持分離（沿用 spec 原決策），理由：
- **前後端放一起無安全性問題**（環境變數不會進前端 bundle），但分離換來服務各自獨立部署
- SEO 若未來需要，可在 Railway 端加 SSR，不受目前架構限制
- 兩個服務都可綁自訂網域，網址可讀性非決定因素

代價：需設定 CORS（`ALLOWED_ORIGINS` 環境變數）。

### 3. 手機端 DB 存取沿用本機的同步 psycopg，不用 SQLAlchemy async

exercise-together 用 `asyncpg` + SQLAlchemy async ORM，但本專案本機端 `upload.py`
已經是同步 `psycopg` 直連、不用 ORM。手機端只是唯讀 SELECT，量小，
沿用同步 psycopg 風格比引入 async ORM 更一致、更簡單。

### 4. 認證邏輯照搬 exercise-together 的三段式查詢，改寫成 SQL

`google_sub` 查 → 查不到 fallback `email` → 首次登入寫回 `sub`，邏輯與 spec §6.1 一致，
只是把 SQLAlchemy ORM 呼叫換成原生 SQL（`app/routers/auth.py`）。

### 5. Google Client ID／API 網址用 `mobile-web/config.js`（不進版控）注入

這兩個值本來就會出現在前端原始碼中（非密鑰），但為了讓同一份程式碼在本機測試與
正式環境間切換網址方便，改用 `window.PODSCRIPT_API_BASE` 全域變數，
由不進版控的 `config.js`（範例見 `config.example.js`）提供。

## 本機測試結果（2026-09-18）

`mobile-backend/venv`（Python 3.12，需與系統內建 3.9 區分——程式碼用了 `str | None`
語法，3.9 建 venv 會炸；改用 `/opt/homebrew/bin/python3.12`）。

**踩到的坑：** `app/main.py` 原先 `from .routers import auth, episodes` 寫在
`load_dotenv()` 之前，導致 `app/auth.py` 模組層級的 `SECRET_KEY = os.environ.get(...)`
在 `.env` 尚未載入時就被算成空字串，之後任何 JWT 一律判定為 invalid。
修正為 `load_dotenv()` 提到最前面，任何內部模組 import 之前執行。

驗證通過：
- 健康檢查、無 token 存取回 401
- 列表／詳細頁正確讀出 Supabase 現有兩集資料
- 中文搜尋 `q=房仲` 命中（`pg_trgm` 生效，需用 URL-encode 過的查詢字串測試，
  curl 直接夾中文會被 uvicorn 判定為 invalid HTTP request）
- 標籤篩選 `tag=房地產` 正確
- 白名單外使用者 id 簽的 token → `get_current_user` 查無此人 → 401

**尚未測試：** 真實 Google 登入流程（`/api/auth/google`），因 `GOOGLE_CLIENT_ID`
目前是空值，需使用者建立 OAuth Client ID 後才能實測。
