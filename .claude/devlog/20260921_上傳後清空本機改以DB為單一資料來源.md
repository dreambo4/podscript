# 20260921 上傳後清空本機，改以 DB 為單一資料來源

## 目標

使用者提出：本機 `audio/` 下的檔案都只是過渡用的暫存檔，不上 git；
可以上 DB 的功能都上 DB，上傳完成後本機不再留多餘檔案。
未來整套搬遷到其他電腦，**只要搬程式就好**。

## 起點：先釐清「哪些真的用不到」

原本的認知是上傳後只刪 `source.mp3` / `audio.wav`，其餘六個檔案留著：

| 檔案 | 大小 | 原本的用途 |
|---|---|---|
| `whisper.json` | 3.8 MB | whisper 原始輸出，轉錄階段快取 |
| `diarize.json` | 20 KB | pyannote 說話者時段，分離階段快取 |
| `transcript.json` | 62 KB | 合併後結果，`load_result()` 讀它 |
| `transcript.txt` | 50 KB | 可讀版本，`summarize()` 餵給 `claude -p` |
| `result.json` | 3 KB | 摘要／心智圖／標籤 |
| `job.json` | 1 KB | 任務狀態，服務重啟後還原 |

比對 DB 後確認 `transcript` / `speakers` / `summary` / `mindmap_mermaid` / `hashtags`
都已完整上傳，段數與本機一致（64 / 80 / 178）。

### 查到的兩個落差

1. **`transcript_text` ≠ `transcript.txt`**
   `upload.py` 存的是 `"".join(seg.text)`，**沒有時間戳與說話者名稱**
   （16375 字元 vs 本機 50090 bytes）。但 `transcript` jsonb 完整，
   可用 `format_transcript()` 即時重建，不需另外存檔。

2. **`mp3_url` 與 `description` 未進 DB**
   `build_payload()` 只送 7 個 episode 欄位，這兩個會永久消失。
   使用者判定兩者都不需要，故不加欄位、不動 DDL。

另外 `cmtwkni8z0f2t01tp4sxqes0j` 的 provenance 六欄全空 —— 該集早於 provenance 功能，
**本機也是空的**，非 DB 漏存。

### 真正的阻礙不是檔案佔空間

`list_episodes()` 是 `AUDIO_ROOT.glob("*")` 掃本機目錄建出來的，
`get_episode` / `rename_speakers` / `regenerate` 全依賴 `pipeline.load_result(directory)`。
**本機清空後整個列表頁會空掉、所有單集 404** —— 這才是「只搬程式」無法成立的原因。

## 使用者確認的決策

- **A. 改說話者名稱改走 DB**（失去離線能力）→ 可接受，且希望手機端也能改
- **B. `whisper.json` 不留** → 上傳即代表認可逐字稿，DB 的 transcript + speakers 已足夠
- **C. 現有三集可清**，`mp3_url` / `description` 都不需要

## 異動摘要

### `src/podscript/upload.py`
- `_remove_audio()` → `_remove_local()`：改用 `shutil.rmtree` 清整個目錄
- 新增 `fetch_episode(guid)` / `fetch_all()`：DB → `pipeline.Result` 還原
- 新增 `update_episode()`：改名、重生摘要直接寫回 DB
- 新增 `_row_to_result()` / `_as_json()` / `_iso()` 輔助函式
  （`_as_json` 處理 psycopg 依欄位型別回傳 dict 或字串的差異）

### `src/podscript/pipeline.py`
- `summarize()` 加 `persist` 參數：DB 來源的單集不寫本機檔
- 新增 `_summary_transcript()` context manager：
  沒有 `transcript.txt` 時由 segments 重建暫存檔餵給 `claude -p`
  （仍寫檔，避開 CLAUDE.md 陷阱 #5 的 ARG_MAX 問題），**用畢即刪**，
  且若目錄是為此次重建而生、清空後一併 `rmdir`

### `src/podscript/server.py`
- `list_episodes()` 改為「DB 已上傳的 ∪ 本機處理中的」，本機覆蓋 DB 版本
- 抽出 `_episode_summary()` 組列表欄位
- 新增 `_load_episode()`：本機找不到就從 DB 還原，回傳 `from_db` 旗標
- `get_episode` 回傳新增 `from_db` 欄位
- `update_speakers` / `regenerate` 走 DB fallback，改完寫回 DB
- 新增 `_sync_speakers()`

### 未異動
- `.gitignore` 早已含 `audio/`，不需修改
- 無 DDL（`description` / `mp3_url` 依使用者決定不加欄位）

### 追加：修正「已上傳的集數無法再次上傳」

使用者回報按「再次上傳」失敗，回 400「尚未完成處理，無法上傳」。

**原因**：`build_payload()` 只有 `pipeline.load_result(directory)`，僅讀本機檔案。
上傳後本機已清空 → 回 `None` → 拋錯。`server.py` 的 `get_episode`、
`update_speakers`、`regenerate` 都加了 DB fallback，**唯獨上傳自己漏了**。

**修正**：`build_payload()` 本機讀不到時改用 `fetch_episode()` 取回。

### 追加：重新生成改為不直接寫 DB（使用者選項 B）

原本的實作讓已上傳的集數「重生即寫 DB」，與未上傳集數的行為不一致，
也繞過了 spec §11 決策 10「上傳是手動觸發，可反覆重新生成到滿意再上傳」——
使用者手機上正在看的內容會在確認前就被換掉。

**修正**：`regenerate` 一律只寫本機（`result.json` + `transcript.json` + `transcript.txt`），
由使用者按「再次上傳」才進 DB；上傳後 `_remove_local` 一併清除，
不違背「上傳完本機不留檔案」。同時移除 `pipeline.summarize()` 已無用的 `persist` 參數。

**實測（EP239，實際消耗 claude -p 額度）**：
1. 重生耗時 35 秒 → 本機出現三個暫存檔，**DB 完全未動**（摘要仍為舊版）
2. 按上傳 → DB 更新為新摘要，本機清空（釋出 135 KB），`inserted: false` 走 update
3. 96 段與說話者名稱（博恩／高淑芬醫師）皆完好

**附帶觀察**：重生後標籤與原本完全相同，是 `reconcile_hashtags` 的標籤收斂機制
使新標籤向既有標籤庫靠攏所致；摘要內文確實不同，功能正常。

### 追加：列表改以建立時間排序

使用者要求「單集列表要以建立時間排序，不是節目發佈時間」。
DB 已有 `created_at` 欄位，不需 DDL。

- `FETCH_COLUMNS` 加入 `created_at`，`fetch_all()` 回傳值增為四元組
- `_episode_summary()` 加 `created_at` 欄位，本機來源取 `job.started_at`
- 合併時以資料庫的 `created_at` 優先，本機值僅供尚未上傳者使用
- 排序鍵由 `published_at` 改為 `created_at`

效果：EP70 是 2023 年的節目，原本會排在最後，現在依實際加入順序排在第二。

### 追加：run.sh 加上 --reload

使用者要求開發時自動重載。關鍵是加 `--reload-dir src` 限定監看範圍：
預設監看整個專案目錄，轉錄期間 `audio/` 持續寫入中間產物會不斷觸發重載，
反而會中斷處理中的轉錄。啟動訊息確認只監看 `src/`。

## 影響範圍

- **行為改變**：上傳後本機目錄整個消失，該集之後一律由 DB 還原
- **不可逆**：`whisper.json` 清除後無法回到未經後處理的原始轉錄；
  mp3 網址帶時效參數，音檔刪除後也無法重新下載 → **已上傳的集數不可重跑轉錄**
- **新依賴**：已上傳單集的檢視與改名需要 DATABASE_URL 可用（失去離線能力，使用者已同意）
- **資料**：`audio/` 已清空，三集現存於 Supabase
- **未涵蓋**：`mobile-backend` 未異動；手機端若要支援改說話者名稱需另加 endpoint
