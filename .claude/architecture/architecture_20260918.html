podscript 架構圖

兩套完全獨立的服務：本機重運算管線負責產生逐字稿／摘要，手機端輕量 API 負責唯讀查詢。兩者不共用程式碼，只透過 Supabase 交換資料。

本機（M1 Mac mini）
雲端（Railway / Firebase）
Supabase（共用資料層）

本機處理 localhost

完整逐字稿管線，需要 Apple Silicon 的 Metal GPU 加速，設計上就不會、也不能搬上雲。

web/前端

原生 HTML + app.js，操作介面與進度輪詢（GET /api/jobs/{guid}，2 秒一次）。

src/podscript/server.pyAPI

本機 FastAPI，接收任務、回報 job 狀態，狀態存在 audio/{guid}/job.json。

transcribe / diarize運算

whisper.cpp（Metal GPU）+ pyannote 分辨說話者，OpenCC s2twp 轉繁體。

summary.py運算

呼叫本機 claude -p 產生摘要／心智圖，逐字稿寫檔傳入避免 ARG_MAX。

upload.py手動觸發

使用者確認品質後才手動上傳，寫入 Supabase，可反覆重跑到滿意為止。

手機端唯讀查詢 Railway + Firebase

跟本機完全獨立的一套服務，只做「登入 + 唯讀查詢」，不 import 本機任何程式碼。

mobile-web/前端

原生 HTML 唯讀介面，部署於 Firebase Hosting，透過 config.js 指向 API 網址。

mobile-backend/API

獨立 FastAPI app，計劃部署於 Railway。Google id_token 驗證 + JWT，唯讀 SELECT（同步 psycopg）。

routers/auth.py認證

google_sub 查 → 查無則 email fallback → 首登寫回 sub → 簽發 JWT。

routers/episodes.py查詢

列表（搜尋＋標籤＋分頁）與詳細頁，中文搜尋靠 pg_trgm。

關於你剛才看到的 GET 輪詢 log：那是 web/app.js 打本機 server.py，完全發生在 localhost 內部，跟 Railway 無關，不會有計費或負擔問題。

等 mobile-backend 上線 Railway 後，那邊的流量只會是手機端偶爾打的唯讀查詢（/api/episodes、/api/auth/google），本身沒有輪詢機制，量會很小。
