## 1. 背景

研究專案（待辦第 9 項，2026-10-09 實作）目前只是「分類」：

- 本機：左側清單上方的下拉選單依專案篩選；「管理專案」對話框改名、說明、刪除
- 手機：專案列表頁（名稱、說明、已上傳篇數），點卡片 = 用該專案篩選首頁列表
- 資料：`projects`（名稱、說明）＋ `project_items`（`project_id`、`episode_guid`、`added_at`）

也就是說，專案本身沒有「頁面」——點進去看到的仍是一般列表。
使用者希望每個研究專案有自己的頁面，但還沒有具體想法，本文件先列提案，再由訪談收斂。

## 2. 現有可用的素材

做專案頁時，不新增任何資料就能拿來用的東西：

| 素材 | 來源 | 備註 |
|---|---|---|
| 各篇標題、來源、發布時間、時長、封面 | `episodes` | 論文的來源是期刊名稱 |
| 各篇摘要、心智圖、章節 | `episodes.summary`、`mindmap_mermaid`、`chapters` | |
| 各篇主題標籤 | `episodes.hashtags` | 最多 5 個，可彙整成專案的標籤分布 |
| 全文 | `episodes.transcript_text` | 已有 `pg_trgm` 索引，可做專案內搜尋 |
| 歸入時間 | `project_items.added_at` | 可看出研究的進展順序 |
| 思辨練習紀錄 | Supabase Storage `notes` bucket（`notes/<guid>.md`） | 只有做過練習的集數才有；repo 公開所以不進 git |

## 3. 提案

依「要不要新增資料」與「會不會消耗 Claude 額度」分三層。三層可以只做一部分，也可以分批做。

### 3.1 第一層：專案總覽（不新增資料、不耗額度）

把現有素材重新組合成一頁。

- **A. 專案首頁**：名稱、說明置頂；下方列出專案內容，可切換「依發布時間」「依歸入時間」排序，
  可依類型（Podcast、文章、論文）分組
- **B. 統計列**：篇數、各類型篇數、Podcast 總時長、最早與最新的發布時間
- **C. 標籤分布**：彙整各篇 `hashtags`，出現次數多的排前面；點標籤 = 只看帶這個標籤的篇目。
  用來一眼看出這個專案實際上在談哪些子題
- **D. 時間軸**：依發布時間排成一條線，看某個議題的討論如何隨時間變化
- **E. 專案內搜尋**：只在這個專案的內容裡搜全文，結果列出命中段落，Podcast 附時間戳可直接跳
- **F. 候選內容**：用標籤交集找出「還沒歸入、但標籤和這個專案很像」的篇目，一鍵歸入。
  純資料庫比對，不呼叫模型

### 3.2 第二層：使用者自己的研究內容（要新增資料表，不耗額度）

專案頁不只是看 AI 產的東西，也放使用者自己寫的東西。和思辨練習「自己先想」的方向一致。

- **G. 研究問題**：專案建立時寫下「我想搞清楚什麼」，可以列多個問題，各自標記
  「還沒有答案／有初步想法／已釐清」。現有的「說明」欄位可能就夠用，也可能要拆成清單
- **H. 專案筆記**：一份隨時更新的自由筆記（Markdown），記錄目前的理解與還不懂的地方
- **I. 摘錄**：在單集頁選取一段逐字稿或論文原文，加入某個專案的摘錄板，
  自動附上來源與時間戳；可加一句自己的評語。寫報告或回頭查證時最常用到
- **J. 閱讀狀態**：每篇標記「待讀／已讀／已做思辨練習」，專案頁顯示進度
- **K. 思辨練習紀錄彙整**：專案頁列出各篇的思辨練習紀錄；
  對應 `.claude/思辨練習.md` 第 5 步「每累積 3 到 5 集回顧盲點」，以專案為單位回顧最自然

### 3.3 第三層：跨篇整理（耗額度，本機 `claude -p` 手動觸發）

`.claude/todo.md` 第 9 項已記錄「專案層級的綜合整理每次都會消耗額度，等穩定後再討論」，這裡先列選項。
沿用既有原則：本機產生、手動觸發、可反覆重新生成、滿意後才寫入資料庫。

- **L. 主張對照表**：從各篇抽出主要主張，整理成「主張 × 來源」的表，
  標出哪些主張被多篇支持、哪些互相矛盾、哪些只有一篇提到。
  **只整理「誰說了什麼」，不判斷誰對**，以免違反思辨練習「AI 不給結論」的原則
- **M. 專案心智圖**：把多篇的心智圖合併成一張專案層級的地圖
- **N. 缺口提示**：根據研究問題（G）列出「目前內容還沒回答到的部分」，
  建議下一篇該找哪類來源（例如缺第一手資料、缺反方觀點、缺數據）
- **O. 專案層級的思辨練習**：AI 依對照表提問（例如「A 和 B 的說法衝突，你目前比較相信哪個，為什麼」），
  使用者作答；延伸自思辨練習第 5 步的「AI 抽主張 → 使用者作答 → AI 追問」構想

### 3.4 匯出

- **P. 專案匯出**：整個專案匯出成一份文件（研究問題、筆記、摘錄、各篇摘要、參考來源清單），
  沿用「PDF 用瀏覽器列印樣式」的決策；論文可產生參考文獻格式

### 3.5 頁面配置（2026-10-09 使用者看過草稿，認可方向）

使用者對「第一眼要看到什麼」還沒有想法，依已定案項目先提一版。
可點的草稿（示意資料，可切換手機／本機）：https://claude.ai/artifact/3s8TmJqLbpLoZBr6t7wHrw
三個用途（整理收藏、追蹤議題、做決定）的共同點是「我在搞清楚什麼、目前有哪些來源」，所以由上而下：

```
┌──────────────────────────────────┐
│ 專案名稱                 [編輯]   │
│ 說明（一兩句）                    │
├──────────────────────────────────┤
│ 研究問題                          │
│  ○ 問題一          還沒有答案     │
│  ◐ 問題二          有初步想法     │
│  ● 問題三          已釐清         │
├──────────────────────────────────┤
│ [內容] [對照表] [心智圖] [筆記]    │  ← 分頁
├──────────────────────────────────┤
│ 內容分頁：                        │
│  [搜尋這個專案…]                  │
│  時間軸（依發布時間，可切歸入時間） │
│   2024-03  Podcast  標題…         │
│   2025-01  論文     標題…         │
│   2026-09  文章     標題…         │
│  [全部][Podcast][文章][論文] [可能相關]│ ← 最後一顆虛線框
│  選「可能相關」時列出候選：         │
│   標題…  #標籤 #標籤      [歸入]   │
└──────────────────────────────────┘
```

- 內容清單本身就是時間軸（D），不另做一個區塊
- 候選內容（F）不另開區塊，放在類型篩選列最後一顆「可能相關 N」標籤：虛線框、連結圖示，
  與類型標籤區分；點選後列出候選（依共同標籤數排序，顯示共同標籤），每筆可「歸入」；沒有候選時不顯示這顆標籤
- 「產生 AI 整理」只有一顆，放在專案標題卡片底部（本機）：對照表、心智圖、缺口是同一次產生，
  按鈕集中一處，避免誤以為只更新某一項。卡片顯示「何時、依幾篇摘要產生」，有新歸入的篇目未納入時標出篇數，
  按鈕轉為醒目樣式；手機只顯示狀態，有未納入的篇目時提示「到本機重新產生」
- 對照表、心智圖分頁頂端只顯示產生日期，不放按鈕；從未產生過時顯示「尚未產生」
- 「AI 建議問題」是另一次呼叫，按鈕留在研究問題區塊標題列（本機）
- 每個研究問題點開後依序顯示：「我的筆記」（Markdown，檢視／編輯切換）、「AI 整理的缺口」（哪些篇有談到、還缺哪類來源）
- 研究問題左側有拖曳握把，可手動排序；列上顯示狀態、談到的篇數、是否有筆記
- 研究問題清單下方：AI 建議問題區（勾選後「加入所選」，或「都不要」）

## 4. 技術上要先注意的事

1. **額度**：第三層每次都要把多篇內容餵給模型。一個專案 10 集 Podcast 約 20 到 30 萬字，
   不能整份逐字稿丟進去，要改用各篇的摘要或章節當輸入；仍須寫檔讓 `claude -p` 讀，不可當參數（ARG_MAX）
2. **未上傳的集數**：本機可以把未上傳的集數歸入專案，但手機看不到。
   第三層若在本機產生，要決定未上傳的集數算不算進去
3. **思辨練習紀錄在 Storage**：手機要顯示（K）的話，手機後端要能讀 `notes` bucket；
   目前只有本機 `scripts/notes.py` 會讀寫
4. **新資料表**：研究問題（含排序欄位、狀態、個別筆記）、專案筆記、AI 整理結果（對照表、心智圖、缺口、建議問題），DDL 一律由使用者執行
5. **兩端**：手機和本機要不要長得一樣、功能是否對等，會大幅影響工作量

## 6. 已定案

**2026-10-09 訪談（使用者決定）**

1. **用途**：單純整理收藏、長期追蹤議題、做一個決定（不以寫文章或報告為主 → 摘錄 I、匯出 P 優先度低）
2. **裝置**：手機與本機都要有專案頁，本機功能較完整
3. **使用者自己的內容**：要「研究問題」（G）與「專案筆記」（H）；不需要摘錄（I）
4. **AI 跨篇整理**：要做，但只整理「誰說了什麼」，不判斷誰對、不下結論
5. **第一層**：要時間軸（D）、專案內搜尋（E）、候選內容（F）
6. **第三層**：要主張對照表（L）、專案心智圖（M）、缺口提示（N）。
   缺口提示只列「研究問題還沒被哪篇回答到」與「可以找哪類來源」，不給答案
7. **思辨練習紀錄**：不出現在專案頁，維持獨立
8. **手機分工**：手機可以編輯研究問題與專案筆記；AI 整理只在本機產生，手機只看結果
9. **額度**：AI 整理手動觸發，只用各篇摘要當輸入（不用章節、不用逐字稿全文）；
   沒有摘要的篇目不算進去
10. **頁面配置**：照 §3.5 的方向做（研究問題置頂，下方分頁：內容／對照表／心智圖／筆記）
11. **筆記用 Markdown**：使用者自己打 Markdown，不需要工具列與格式按鈕（套件見 §3.6）
    - 兩端都是「檢視／編輯」切換，切回檢視時儲存；檢視顯示轉換後的完整內容
    - 本機編輯用 Markdown 編輯器（標記即時上色）；手機不用編輯器，編輯是一般文字框
    - 文字顏色一律用現有主題色（深色模式曾出現深藍字配深底，看不清楚）
12. **AI 建議研究問題**：AI 一次產生 3 個備選問題，使用者勾選後才加入研究問題清單
13. **研究問題手動排序**：清單可拖曳調整順序，順序要存起來
14. **研究問題的個別筆記**：每個研究問題可以寫自己的筆記（同樣是 Markdown 檢視／編輯切換），與專案筆記分開
15. **可能相關的入口**：放在類型篩選列旁的一顆標籤，樣式要與類型標籤有區別（見 §3.5）
16. **筆記區塊不顯示操作提示文字**（如「直接打 Markdown」），使用者已熟悉 Markdown（2026-10-09）
17. **本機專案頁是獨立頁面**（`/project#<id>`），不顯示左側單集清單，也不與單集內容混在同一頁（2026-10-09）；
    頁首有「← 單集清單」與專案切換選單，點篇目回到單集頁
18. **專案管理頁**（`/projects`，2026-10-09；第二輪訪談後改名為「研究專案」總覽，見 §6.1）：首頁不改版面，只在頁首加入口。
    左側是單集清單，右側是專案資料夾一格一格排列，把單集拖進資料夾歸類；點一篇單集，它所在的專案亮起來，
    亮起的資料夾可移出；最後一格可新增專案；歸類與移出後的提示可復原
19. ~~首頁「管理專案」對話框可新增專案~~：第二輪訪談後拿掉整個對話框，新增改在專案總覽（§6.1）

### 6.1 專案入口與流程（2026-10-09 第二輪訪談，使用者決定）

背景：專案相關功能散在五個地方（首頁左側篩選、「專案頁」按鈕、「管理專案」對話框、頁首「專案管理」、
單集頁「研究專案」區塊），「管理專案」與「專案管理」做的事不同，使用者找不到新增專案的地方。

**使用情境**
- 打開本機網頁的目的四種都有：處理新內容、繼續研究某主題、找以前的內容、整理歸類
- 歸類時機兩種都有：讀完當下順手歸、累積一批再整理
- 開新專案：多半是對某主題有興趣，在網路上看到相關文章或影片就整理進專案；也會整理時發現一群相關內容才開
- 發現內容主要在**手機**（先存進手機的「待處理」，回電腦再處理）
- 首頁左側的依專案篩選不需要

**決定**
1. 入口收斂成三個：
   - 首頁頁首「研究專案」→ 專案總覽（`/projects`）：左側單集清單、右側專案格子；可新增專案、拖曳歸類；點格子進專案頁
   - 專案頁（`/project#<id>`）：研究問題、內容、AI 整理、筆記；在這裡改名、改說明、刪除
   - 單集頁的「研究專案」區塊：讀完順手歸類
   - 拿掉首頁左側的專案篩選、「專案頁」按鈕與「管理專案」對話框
2. 專案格子只顯示名稱、篇數、最近加入時間；不顯示說明、不放「看內容」；點格子進專案頁

## 8. 資料結構（Claude 提案，待使用者確認後由使用者執行 DDL）

現有 `projects`、`project_items` 不動結構，另加：

1. `projects` 加專案筆記欄位（一個專案一份，不另開表）
2. `project_questions`：研究問題，含狀態、排序位置、個別筆記
3. `project_insights`：AI 整理結果，一個專案一列，重新產生時整列覆蓋

```sql
-- 研究專案頁面（spec: specs_20261009_研究專案頁面.md）

-- 1. 專案筆記
alter table projects add column if not exists note text not null default ''
  check (length(note) <= 50000);
alter table projects add column if not exists note_updated_at timestamptz;

-- 2. 研究問題
create table if not exists project_questions (
  id          uuid primary key default gen_random_uuid(),
  project_id  uuid not null references projects (id) on delete cascade,
  text        text not null check (text <> '' and length(text) <= 200),
  status      text not null default 'open'
              check (status in ('open', 'partial', 'resolved')),  -- 還沒有答案／有初步想法／已釐清
  position    int  not null default 0,                           -- 手動排序，小的在前
  note        text not null default '' check (length(note) <= 20000),
  created_at  timestamptz not null default now(),
  updated_at  timestamptz not null default now()
);
create index if not exists project_questions_project_idx
  on project_questions (project_id, position);

-- 3. AI 整理結果（本機 claude -p 產生，手機只讀）
create table if not exists project_insights (
  project_id      uuid primary key references projects (id) on delete cascade,
  claims          jsonb,          -- 主張對照表
  mindmap         text,           -- Mermaid mindmap 語法，沿用單集的心智圖渲染
  gaps            jsonb,          -- {"<question_id>": {"covered": [guid...], "missing": ["..."]}}
  source_guids    text[] not null default '{}',  -- 產生時用到的篇目，用來提示「有新篇目未納入」
  generated_at    timestamptz,
  suggestions     jsonb not null default '[]'::jsonb,  -- 建議問題 [{"text": "...", "why": "..."}]
  suggested_at    timestamptz,
  provenance      jsonb not null default '{}'::jsonb   -- 模型與版本
);

alter table project_questions enable row level security;
alter table project_insights enable row level security;
```

設計說明：
- 狀態存文字而非 0/1/2，資料庫裡直接看得懂
- 排序用 `position` 整數；拖曳後前端送出整組順序，後端在同一個交易裡重寫 `position`
- 缺口（gaps）以問題 id 為鍵：問題刪除後殘留的鍵直接忽略；產生之後才新增的問題顯示「下次產生時才會分析」
- 建議問題只存「尚未處理」的那批：勾選加入的轉成 `project_questions`，其餘連同「都不要」一起清空
- 刪除專案時，問題與 AI 整理一併刪除（`on delete cascade`）；`project_items` 本來就會一起刪
- RLS 開啟不設 policy，與 `projects` 相同，只由本機與手機後端直連存取

**兩台裝置同時改筆記**：手機和本機都能編輯筆記與研究問題。儲存時帶上「開始編輯時載入的內容」
（專案筆記為 `base`、研究問題為 `base_note`），資料庫的內容已不同就回 409，前端提示「另一台裝置已修改，
請重新載入」，不直接覆蓋。比對內容而不比對 `updated_at`：另一台只改了問題狀態時，筆記並沒有衝突，
不該擋下。

## 10. AI 產生（本機 `claude -p`）

沿用 `SummaryProvider` 抽象層與既有規則：輸入寫檔讓 `claude -p` 讀，回傳要擷取 JSON 區塊。

**輸入**：專案名稱、說明、研究問題（含 id）、各篇的標題、類型、來源、發布日期、摘要。
只用摘要（§6 第 9 點），沒有摘要的篇目略過並在結果註明。

**兩個獨立的按鈕、兩次呼叫**：
1. 「產生 AI 整理」：一次呼叫產生對照表、心智圖、缺口三項（同一份輸入，分三次呼叫只會多花額度）
2. 「AI 建議問題」：另一次呼叫，只產生 3 個建議問題；輸入同上，加上現有問題以免重複

**提示詞必須寫明的界線**（§6 第 4、6 點）：
- 對照表只整理「哪篇說了什麼」，標記為「有此主張」「說法不同」「沒提到」；不評斷哪篇正確、不下結論
- 缺口只列「哪些篇有談到這個問題」與「還缺哪類來源」，不回答問題本身
- 建議問題每題附一句理由，說明是從哪些篇目或對照表的哪個缺口看出來的

**模型**：沿用 §9.2 實測後選定的摘要模型；是否改用其他模型由使用者決定。
